看 MAI-UI 的资料，我最先想到的是，AI 如果真的能替人操作手机，一些原来要自己来回点的事情，可能会变轻松。

但很快又想到另一头：它点错了呢？

回答错一句话，我还能停下来核对。操作已经发出去，可能是提交了一份表单、修改了订单，或者把消息发给了别人。这个时候，体验就不能只看它操作得多快，还要看自己是否知道发生了什么，能不能停下，后面怎么处理。

我想顺着这个问题展开。MAI-UI 带来的变化，不只是一种模型能力，也会影响任务怎样描述、产品怎样提供状态、团队怎样看待点击和完成。差旅报销这个例子尤其适合拿来推一遍，因为它看起来重复，里面却有不少需要确认的细节。

## 先分清公开能力和我的设想

MAI-UI 是阿里通义团队的 GUI Agent 项目。2025 年 12 月的 [技术报告](https://arxiv.org/abs/2512.22047) 讨论了界面定位、移动端任务执行，以及与用户交互、工具调用、端云协作等问题。

我比较在意报告对动态环境和现实部署难点的讨论。它没有理由被简化成「看得懂任意 App，从此可以全自动操作」。基准成绩说明某些条件下的表现，不是对用户手机里所有任务的承诺。

从产品角度理解，可以先拆成几件事：看懂当前屏幕上的对象，判断下一步动作，执行点击或输入，再根据新的页面状态继续。GUI Agent 的关键是需要不断读取反馈，不能只按一张固定脚本从头点到尾。

视觉定位解决的是目标在屏幕哪里，任务规划处理的是接下来做什么。定位对了，不代表任务理解一定对；点中了按钮，也不代表业务已经成功。登录失效、页面变化、弹窗、加载中，都可能改变下一步。

报告里的 MCP 指 Model Context Protocol，是连接工具与上下文的一种协议，不是一个叫「跨 App 协同协议」的东西。通过工具调用和通过屏幕操作，是两类可以组合的执行方式，不能混着理解。

### 订票这个愿望，要拆开来看

假设我说「明天北京去上海，八百元以内，订好以后通知助理」。这句话看起来清楚，实际仍然缺少信息。

选择哪个时间段，是否接受中转，价格包含什么，谁是乘机人，哪个联系人是助理？系统已经知道的资料，也可能需要确认是不是这一次要用的。

我会期待它先查到候选方案，展示关键差异，让人确认，再进入后续流程。涉及支付和发消息，授权也要明确。这是一种期望中的产品设计，不是在说 MAI-UI 已经可以替我在所有应用里稳定完成这件事。

「一句话发起任务」可以是入口，「一句话之后再也不需要人」却是另一种要求。二者不能直接画等号。

## 点击指标会变，但人没有消失

如果一部分操作由 Agent 完成，原来只统计点击和页面停留的做法，确实需要重新解释。

用户本人进入页面，和代理为了完成任务进入页面，意图可能不同。一次完成任务产生了很多点击，也未必代表参与度高，可能是它在反复寻找入口。停留短，有时是效率提高，有时是根本没拿到需要的结果。

我会想在原有指标之外补几个问题：

- 发起了多少任务，哪些真正完成，完成如何确认？
- 哪些步骤需要人介入，介入以后能否继续？
- 任务失败时有没有重复操作，是否产生了副作用？
- 用户第二次还愿不愿意授权类似任务？

这不代表 DAU、点击率或 A/B 测试都失效了。人仍然使用产品，界面的清晰程度仍然影响人工操作和接手。需要做的是区分使用方式，找到和目标有关的评价口径。

### 想象中的自动化早晨，容易省略什么

一种常见的设想是，助手早上看天气、买衣服、约车、处理账单，人在睡觉，事情就办好了。作为想象它很吸引人，但我会忍不住往里补问题。

降温就要买衣服吗，家里是不是已经有？今天有会议，就一定要约车吗？账单金额是否异常，发给同事的消息是否需要本人看过？

这些不是在否定自动化，而是在区分提醒、建议、准备和执行。查天气可以自动做，给出穿衣建议也可以；替人消费就不只是多调用一个工具。

把这些权限写清楚以后，任务可能没有演示里那么顺畅到底，却更接近我愿意长期使用的助手。用户的界面也不会只剩后台日志，它还是核对、修改和收回授权的地方。

## 拿差旅报销走一遍

传统差旅报销常涉及出票记录、发票、公司系统和审批。接口能提供标准数据时，通常值得优先考虑；没有接口或接入不方便时，GUI 操作可能多提供一种办法。

我不想把这说成 API 没用了。屏幕会改版，字段会移动，权限和登录状态也会变化，GUI Agent 同样需要维护。

下面是一个假设方案，用来想清楚任务设计，不是已上线案例，也不承诺零开发成本。

### 触发点要能解释

可以由用户主动说「帮我准备这次出差的报销」，也可以在获得明确授权后，根据某类通知提醒。自动读取手机短信本身涉及权限和平台限制，不能默认每台设备都能做到。

触发后先确定是哪一次行程。记录有几张票、是否改签、要提交给哪个主体，都可能影响后面的数据。任务身份不清楚，不应急着往下填。

### 读到的内容，需要带着来源

Agent 打开对应应用或文档，找到行程、金额和日期。这里要知道，显示的是票价、实付金额还是含退改费用的总额，不能把一个醒目的数字直接当报销金额。

如果看不清、页面没加载完、缺正式凭证，就应该标明缺失。能把识别结果指回原始页面或附件，比只给一组数字更方便人工检查。

提取字段可以先形成草稿，暂时不要提交。哪部分来自原始材料，哪部分来自公司规则，也应区分。

### 跨应用填写，不等于已经完成

进入企业工作台、选择报销类型、填写字段、附上凭证，这些动作可以编排，但每一步都可能遇到不同情况。

系统里已有同一份申请怎么办？选错了项目代码怎么办？附件上传中断怎么办？提交后没有成功提示，是重试还是先查记录？

这些细节决定它会不会重复报销，或者让人以为完成了、实际只停在草稿。任务状态不能只写成「执行中」和「成功」两种。

### 接手时，人要看到什么

最终确认页，我希望看到行程、金额、附件、报销归属和待补信息，而不只是一句「已填好，是否提交」。

如果中途失败，最好能保留已经完成的部分，明确停在哪里。人改完一个字段后，是从当前状态继续，还是必须整条流程重来，也会影响使用意愿。

人机协同放在这里就不抽象了。人工确认不是装饰性的最后一个按钮，而是有足够信息让人作判断。确认对象发生变化时，之前的授权也不应该悄悄套用。

这套流程需要状态管理、权限、异常处理和测试。GUI 能减少某些接口依赖，不会让这些工作自动消失。

## 产品可能需要怎样适应

### 让服务更容易被明确调用

如果平台提供稳定的接口、清楚的字段含义和状态反馈，Agent 不必每次猜屏幕。GUI 可以补充没有接口的部分，两者没有必要对立。

对自己的产品，我会先检查操作语义。一个「确定」按钮究竟确定什么，提交是否可撤销，价格字段含不含税，失败有没有可识别的原因。人看不懂的地方，模型未必就能猜对。

界面文字、无障碍标签、结构化返回和业务状态是不同层面的东西。给 Figma 写备注，不代表运行中的 Agent 就能读到；这些含义需要由实际产品实现出来。

### 垂直任务仍然需要理解业务

通用模型能识别页面，不代表知道每个行业怎样判断任务成功。差旅报销、售后处理、材料准备，都有自己的规则。

医疗或法律场景可以考虑辅助整理材料、预约或提示需核对的条目，但不能因为 Agent 能操作，就把专业判断和责任也一并交出去。自动化范围需要比一句「行业智能体」具体得多。

我会先从重复、边界相对清楚、失败后可恢复的任务看起。不需要一开始做一个什么都能接的助手。

## 我想补的三种能力

### 把要求描述成能检查的输入和输出

JSON Schema 这样的结构可以帮助约束字段，但不会替我决定业务含义。先说清触发条件、动作和预期结果，再考虑用什么形式表达。

比如查询航班，输入是出发地、目的地和日期；输出是候选列表或明确的失败原因。实际订票则还要加乘机人、价格确认和授权，不能把两项任务混成一个动作。

「优化体验」太泛，「出现库存变化时暂停提交并展示新信息」就比较容易讨论。写这种说明，也有助于和研发对齐。

我会拿一个现成功能练习，把成功状态、失败状态和不可自动继续的条件写出来。不是只写按钮颜色和位置，也不是放弃这些界面细节。

### 把状态和恢复一起画出来

状态机听起来技术化，想的其实是任务走到哪了、下一步允许做什么。

退款申请可以是待提交、处理中、完成、被拒绝、待人工处理。中间超时以后，要查原来的申请状态，而不是默认重新发起。当前状态影响下一步操作，这部分要在产品里清楚。

Coze、Dify 的工作流可以用于练习任务拆解，但不等于学会它们就掌握了 MAI-UI 的实现。工具连接、权限和设备执行还有区别。

如果做一个周报助手练习，我会先让它读取获准的资料、生成草稿、交给人检查，再决定是否发送。先把「看一下」留在流程里，比第一次就自动发到群里稳妥，也方便知道生成的问题出现在哪。

### 提前写几种不该继续的情况

测试不需要为了凑数先写一百条，先覆盖影响最大的几类。

价格缺失、按钮被遮挡、页面还在加载、账号已退出、关键资料互相矛盾，这些都可以作为用例。每个用例要写清期望它怎样停，而不只是看能不能最终完成。

转账、购买、发消息、删除内容，要按用户授权和动作后果决定确认规则。不能简单规定低于五百元就可自动支付，小金额重复执行同样可能造成问题。

还要看停止以后有没有信息可用。只说「失败」很难接手；说清已经查到什么、还没执行什么、需要用户补什么，体验会好很多。

这些规则不该只写在 Prompt 里。涉及真正的权限和重要动作，需要系统层面约束。模型答应遵守和产品实际阻止，是两件不同的事。

## 我更想看的下一段演示

MAI-UI 让我对手机里的自动化有了更多想象，也让我更在意演示之外的部分。

如果下一次展示的是页面改了、任务被打断、金额对不上之后，它怎样发现问题、怎样请人确认、怎样继续，我可能会看得更认真。因为那决定了自己是否真的敢把一件事交出去。

我仍然需要一个面向人的产品。哪怕大部分点击由模型完成，我也应该能知道当前状态，理解下一步的后果，并且随时接回来。
