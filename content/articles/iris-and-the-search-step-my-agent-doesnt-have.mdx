今天小红书开源了一个 Search Agent 模型，叫 Iris，35B 和 397B 两个版本，同量级里成绩领先。

## 找报告，靠我自己搜

研报笔记 Agent 现在没有搜索这一步。报告是我自己用搜索引擎搜到的，下载下来丢进去，它负责整理成笔记。

找报告这件事一直是手动的：想看哪个方向，去搜，翻几页结果，挑出像样的，下载，再来。搜得顺的时候几分钟，不顺的时候，半天找不到一份靠谱的。用搜索引擎找报告，最花时间的不是搜，是判断：翻出来的结果里，哪份是原始报告，哪份是转载，哪份只是一篇拿报告做标题的文章。

所以看到 Iris，第一个念头是加一步：给它一个方向，它去找最近的报告，找到了直接进整理流程。

## 前几天，发现有朋友在用

前几天写钢人论证那篇，结论是先别再加功能，先弄清楚有没有真实用户。

这几天有了一点进展：有朋友在用它。在用的是一位做产品经理的朋友，这次是真的在用，拿它整理自己在看的报告。

一个真实用户，不多，但和没有是两回事。这让我对要不要加搜索这件事，比前几天更犹豫了。

## 朋友没提要什么

朋友用下来，没提过要加什么。

没提，有两种可能。一种是现在的功能够用，报告自己找，丢进去整理，这个流程对一个产品经理来说不算麻烦。另一种是还没用到觉得缺什么的地步，用的次数还不多。产品经理用它，自己也知道什么该提、什么不该提，没提，也许真是够用。

我分不清是哪一种，也没去追问。追问本身，就有点像在做用户调研了，那是做产品的人才会做的事。

可不追问，我就没法知道搜索这一步是不是真的缺。能确定的只有一件：缺搜索的，目前是我自己。自己缺的东西，最容易被当成用户缺的东西。

## 想先试试效果

看到 Iris，我的第一反应是想先试试效果。

不是马上加进去，是先单独试：拿几个我最近搜过的方向给它，看它找回来的报告和我自己搜的比，是好是差。好，搜索这一步就有了一个现成的方案；差，就不用想了。

试一下不花多少时间，也不动研报笔记 Agent 本身。试的结果不管好坏，都不影响朋友现在的用法，这一点让我试得比较放心。

## 比什么

真要试 Iris，比的不只是找没找到，还有找到的是不是原始报告，是不是最近的，是不是真的相关。这几样，恰恰是我自己搜的时候最花时间判断的。

它要是能把这一步的判断做好，搜索这一步就值得加。只是找得多、找得快，意义不大，找回来一堆，还得我一份份再判断。

## 仓库里还没有 issue

仓库里，到现在还没有人提过 issue。

有朋友在用，但没人提 issue，这两件事放在一起，说明它现在的用户，是会直接来找我的人，不是会去仓库留言的人。

这其实是一个很清楚的信号：它还没有长成一个开源项目该有的样子。开源项目的用户，是那些不认识作者、遇到问题只能去仓库说的人。现在用它的，都认识我。

所以说它越做越像产品，现在还只是一个担心。它离一个真正的产品，还差着那些不认识我的用户。

## 最担心的是越做越像产品

可我最担心的，不是它效果好不好，是加上以后，这个东西越做越像一个产品。

研报笔记 Agent 一开始，是几个晚上做给自己用的。开源以后，有了仓库；朋友用了，有了用户；如果再加上搜索，它就从一个整理工具，变成了一个从找到整理全包的东西。每一步都顺，顺下来，离我去年说的只给自己用越来越远。

钢人论证那次，我答的是没人用就停。现在有人用了，停的理由弱了一点。可有人用，和我愿意把它当产品维护，还是两件事。

## 先试，不加

所以现在的决定是：Iris 先试，不加。先试，是给自己留一个知道；不加，是给它留一个不变。

试的结果留着。等朋友那边用上一阵，看是不是真的缺搜索这一步，再说。如果缺的是朋友，那是一个产品的问题；如果只是我自己想加，那就还是几个晚上的事。几个晚上的事，做了也就做了，不用想太多；一个产品的事，做之前就得想清楚，要不要一直做下去。
