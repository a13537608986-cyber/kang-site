Agent 能搜索、能调工具，一段 demo 顺利跑完，然后呢？到今年，智能体已经不算新概念了。我更想弄清楚的是后面那一步：把它交给真实用户，接进订单和支付流程，我们还缺哪些东西？

Anthropic 最近分享的商业智能体架构指南，正好在讲这些事。材料来自它过去一年参与的几十个真实生产部署，分为架构、延迟与成本、生产运行三个部分。读的时候，吸引我的倒不全是模型怎么思考。购物车归谁管，钱由谁来动，用户说过的话怎么保存，某个团队改了一条提示词之后又该测什么——这些问题没那么显眼，却一个都绕不开。

## 先别急着拆成一群 Agent

### 这里的商业智能体，具体在做什么

指南里讨论的 commerce agent，主要是简化在线目录中的买卖流程。面向消费者时，它要搜索、比价、找替代品、组合订单，结果可能是一个购物车、一份旅行行程、一次套餐变更，或者几个暂时保留的座位。面向商家时，它会回答销售问题，协助促销和活动，处理库存与定价。

这两类场景看起来不同，却可以共用一套核心架构。一个模型围绕目标持续工作，查看上下文，通过工具采取行动，按需加载 Skills 里的流程，碰到不确定的地方向用户澄清，再观察结果，直到任务完成。

注意这张图里没放什么：前面没有意图路由器，先把用户分到不同部门；后面也没有按业务领域排开一组专用子智能体。我读到这里停了一下，多 Agent 分工明明很常见，为什么商业场景反而不急着拆？

### 为什么这份指南更倾向于 Skills

先说拆开的好处。主 Agent 负责拆任务、调度和汇总，子 Agent 各做一部分；有了独立上下文，主模型不用一直背着所有资料，一些工作可以并行，执行过程更容易观察，错误也方便隔离。只是这套分工要有人调度，状态要管理，token 也会多花。

但购物对话不太容易按部门切开。

用户刚说完预算，又补一个配送时间，接着问某件商品能不能替换，这很正常。麻烦在于，购物车、偏好和前几轮约束都得跟着走。拆成多个子智能体后，主模型要反复把这些状态传过去，漏掉一句话，下一步选择就可能偏了。Anthropic 在所讨论的部署中观察到了交接带来的质量损失；一次交接还可能多消耗几倍 token，增加数秒延迟。

领域边界也没有组织架构图那么整齐。一个退货问题，可能同时需要订单历史、当前购物车和商品目录。为了让每个子智能体都能处理，权限和上下文要么重复配置，要么继续来回交接。

Skills 换了个拆法：把某个领域的流程写成指令，加载到已经持有完整对话的主模型里。业务知识仍然可以分模块维护，也能按需控制上下文，不用为了加载一段退货流程，连用户对话一起搬走。随着模型能力增强，它能处理的 Skills、工具和上下文也可以继续增加。

在指南列举的多个企业部署比较中，带 Skills 的单一智能体，质量持续优于“一个大提示词搞定一切”和领域子智能体方案，单任务成本与延迟通常也更低。这个结果有个很重要的前提：商业对话共享的状态很多。我会先看任务能不能切干净，再决定拆不拆，而不会据此认定所有任务都只该用一个 Agent。

深度研究就适合交出去。主模型把子智能体当工具调用，给它独立的上下文窗口，让它自己搜索、读资料、写代码、尝试失败的路径，最后带回结论，过程不必都塞回主对话。还有一种情况：药房或金融服务已经运行着专用智能体，有自己的业务与合规流程。接入时，可以让对方正式接管，直接和用户把这段对话聊完。

这里得分清指南说的“交接”和“委托”。交接改变了对话的所有者，用户接下来直接与领域智能体沟通。委托时，主模型还在中间，单轮调用子智能体，再接过结果继续回答；如果反复进出，共享状态就会反复面临传递损失。名字都叫多 Agent，实际安排很不一样。讨论架构之前，先写清楚谁接着跟用户说话、谁负责保住前面的约束，会省掉不少含混。

### 系统提示词和 Skill，按使用频率分

另一个容易越写越乱的地方，是上下文到底放在哪。

按需加载 Skill 通常要多用一个模型回合。规则明明经常用到，却每次都临时去取，用户就得反复等这一下。按指南给的经验线，预计或已经观察到三分之一以上流量会用到的内容，可以放进系统提示词；其余再考虑 Skills。先从这里划分，后面根据实际流量调整，不用守着三分之一不动。

安全规则、法律要求、品牌约束和关键用户事实，需要一直可见。购物智能体的参考实现，把事实依据、购物车与结账语义、展示规则放在系统提示词里，搜索发现、购买研究、目标规划、客户服务、个性化记忆等流程则通过 Skills 组织。

比起按文档长度硬拆，我更愿意拿一段具体信息来问：什么时候会用到它？漏掉一次会发生什么？如果很少用，又不影响关键约束，那多花一个回合临时加载，也许可以接受。

### 工具接住已有系统，不要把业务逻辑重写一遍

一家电商公司通常已经有搜索与排名、购物车、库存、促销、用户偏好和销售分析系统。这些系统里有长期积累的规则，也有模型拿不到的信号。接入 Agent 时，没必要让模型重新做一遍搜索排序，或者自己推断库存。

工具的边界，可以放在已有系统完成判断、需要模型继续组织任务的地方。搜索接口返回排好序的候选商品，模型再决定给用户看哪些、展示几个、怎么解释推荐理由。这样出了问题，也更容易分清是数据、业务规则还是模型选择出了偏差。

工具返回的结果会直接进入上下文，这里也得收拾一下。接口返回的字段，不意味着模型全都需要。决定推荐什么用得上价格、库存和属性，就保留这些；只供界面加载图片的长 URL，没必要在每行搜索结果里重复。已有接口可以继续用，给模型的那份返回值却不必照单全收。

尤其别只扔回一个错误码。缺少产品 ID，可以直接告诉它：“查询可用性需要产品 ID，请补充后再调用。”真遇到 403 权限错误，则要明确当前无权访问，不能伪装成补个参数就能继续的问题。模型需要据此决定重试、补参数，还是向用户解释为什么做不了。

### 把 UI 组件也当成工具

购物或旅行助手的回答，往往不止一段文字。产品轮播、行程单、座位图、图表，都需要结构化的数据。

把组件数据包进自定义标签，让客户端解析，初看是条近路。可模型对这套标签的熟悉程度，通常不及原生工具调用，嵌套一多就容易不可靠。每加一个组件，系统提示词里还得增加标签定义。历史对话怎么办？重新加载时，要么继续依赖专用解析器，要么维护第二份消息副本，格式出了问题，两边都得照顾。

指南采用的办法是，把呈现商品、呈现行程也定义成工具。模型提供类型化参数，服务端校验、发事件，客户端负责渲染。组件以原生工具调用的格式留在消息列表里，重新打开旧对话时，直接使用这些记录，不必再解析一套自定义标签。

代价在流式体验上。参数全部收齐、缓冲校验完再发出去，子组件就会分步到达，即使开着流式，用户也可能等很久。指南提到启用参数即时流式传输，跳过这层参数缓冲校验，让界面更早收到内容。这里跳过的是传输中的缓冲环节，业务校验可不能跟着取消。不完整数据怎样暂存、能先渲染哪一部分、格式异常怎样恢复，都留给应用处理。

## 慢在哪里，要看整个任务

架构大致定下来，接着看性能。我读这一部分时，一直把“模型吐字快”和“任务完成快”分开看，两者很容易被混在一起。

指南把结果质量放得很重：答案是否相关、任务有没有完成，持续影响留存、参与度和购物车金额。快当然好，可几秒钟就给出一个用不了的结果，用户仍得重来。每个场景都有一笔能接受的“延迟预算”，先弄清楚能等多久，再看怎样少牺牲智能、控制成本，把任务完成在这段时间里。

### 少跑几轮，有时比换一个快模型更有效

按指南的拆法，任务完成延迟是各轮“到最后一个 token 的时间 + 工具处理时间”的总和。能动的地方有三个：少跑几轮，让工具更快，让 token 生成更快。它们有时会互相打架，单独优化其中一项，未必能让用户更早拿到可用结果。

预加载上下文是一个很具体的办法。用户从商品页打开助手，当前商品的数据本来就知道，可以直接带进会话，省掉模型再查一遍的过程。不要把已经拿在手里的信息藏起来，再让 Agent 花一个回合去找。

更强的模型也可能更快。它生成 token 未必占优，但规划好一些、少绕几轮，整件事反而更早结束。指南特别提到，生产任务经常超过五个回合时，更快完成任务的往往是更智能的模型。五回合可以当作排查的信号：先试试是不是规划和工具选择拖了后腿，再决定要不要换成吐字更快的那个。

能够独立执行的工具调用，也可以放在同一轮里并行处理。前提是它们真的互不依赖，不能为了并行，把本来需要等库存结果才能做的决定提前执行。

### 工具本身也可能在浪费时间

换模型解决不了所有延迟。有时一个 Agent 工具内部，又顺序调用了好几个底层服务。用户等的那几秒，有相当一部分花在后端。

这时需要检查底层请求哪些可以并行，哪些可以合成一个专用业务接口，让工具拿到整理好的结果。接口合并本身不会自动变快，关键仍然是内部执行方式，别只是把串行调用藏到更深一层。

调度时也不必总等整轮输出结束。模型正在生成多个工具调用，其中一个已经给出了完整、可执行的参数，就可以先处理它，让模型继续输出后面的内容。这样把模型输出和工具执行排成流水线，能省去中间的空等。指南中的案例把数秒的间隙缩短到了数百毫秒。要等的是当前调用具备执行条件，可不是拿到半截参数就往后端发。

### 用户什么时候看到东西，是另一条时间线

总耗时相同，感受也可能很不一样。一个界面始终转圈，另一个先给出商品卡片，再逐步补全结果，用户知道后者正在做什么。

指南举的商业响应通常有五百到七百个 token，全部生成完再显示，可能就是五秒以上的加载动画，具体还受模型和网络影响。同一个智能体、同一套工具和提示词，只换外层框架的呈现方式，总耗时可以一样，用户第一次看到内容的时间却差很多。组件边生成边呈现，省掉的正是这段对着空白等待的时间。

还可以告诉用户当前在做什么。“正在找临水的酒店”这句话，可以从已有工具参数拼出来，也可以增加一个面向用户的消息参数，让模型自己写。我在意的是它有没有回答眼下的疑问：还在搜索，已经找到候选，还是缺一个条件需要我补充？把实际步骤说清楚就好，不用编造进度，也未必需要很热闹的动效。

### 缓存先看顺序，再看长度

Prompt caching 很容易被当成成本优化的附加项，但请求怎么组织，会直接影响它有没有用。

按指南所述，缓存读取的 token 成本约为新输入的十分之一，常用配置下第二次使用就可能回本；做得好的部署，命中率能达到 90% 到 99%。这些是特定计费与流量条件下的结果，实际仍要看模型、缓存时长、写入成本和复用次数。

缓存按前缀匹配，从开头读到与上次请求第一个不同的字节为止。开头越稳定，越容易复用；前面一变，后面即使大段相同，也可能用不上预期的缓存。只检查“内容大致一样”还不够，顺序和字节一致性都得看。

请求可以按变化频率排成三段。

- 全局段放系统提示词和工具定义，这是复用最频繁的部分，跨回合、跨会话要保持字节完全一致。
- 会话段放当前用户的信息与对话历史，接在全局段之后。
- 易变段放时间、当前页面等频繁变化的信息，排在后面。

把时间戳放在系统提示词最顶部，是一个很容易忽略的问题。看起来只是多了一行日期，却可能让每次请求都从很靠前的位置失去复用。

### 算一次完成任务的钱

选模型和推理强度，光凭感觉很难比。先把任务完成率、相关性、准确性、评估分数的底线，以及 p50、p99 的延迟预算写下来，再让每个候选模型及其推理档位跑完整套用例。尤其别漏掉尾部延迟，中间那批请求表现不错，最慢的那部分却可能让人等不下去。

还有两个细节容易影响比较。

一个是提示词。为当前模型调好的指令，换到另一种模型上未必合适。小模型可能需要更明确的步骤，大模型则可能严格执行之前被忽略的限制。一次结果不好，不一定足够排除候选方案，至少要检查是不是配置本身不匹配。

另一个是计费单位。每次调用便宜，不等于完成任务便宜。如果要多跑几轮，还经常失败重试，账单可能更高。更智能的配置生成 token 稍慢，却可能通过减少复杂请求的轮次，把时间和成本一起省下来。

结果接近时，指南倾向于选更智能的配置，理由仍是质量影响留存，也为未来半年模型能力继续提升留一点空间。这个取舍我能理解，但顺序不能倒过来：预算和评估先过关，再谈这点余量，不能一开始就默认更大的模型总值得买。

## 真正上线以后，还要有人管这些事

### 记忆要落在自己的系统里

用户三月说过自己坚果过敏，六月再来，不该又从头问一遍。商家每周一都看同样三个活动，也没必要每次重新交代需求。这样的记忆很有用，可真要保存下来，马上就会碰到别的问题：哪些信息能记，存多久，又让谁来读？

指南把长期记忆拆成存、写、读三件事。

先看存储。档案很小、只有 Agent 读取时，扁平 Markdown 可以工作；复杂起来以后，已有数据库往往更合适。每条事实是一条小的类型化记录，有键、短值、类别和来源会话，方便查找、更新和追溯。

商家场景里，还得区分账户和操作员。一个商家账户可能被几个人共同使用，记忆不能因此混成一份。店经理不应该因为用了同一个系统，就读到区域经理的对话内容。身份与权限要在读取时生效。

合规要在设计记忆时就考虑，别等选完数据库才补。值得记住的事实，往往也涉及敏感资料。系统允许持有哪些类别，要在写入路径用校验器强制，不能只写进提示词；用户要有查看、纠正、删除入口；记录要设保留期，有遗忘机制；每个部署还要能单独关闭记忆。检索命中率再好，也替代不了这些安排。

写入可以挪到对话之外。每轮结束，或长会话进行几轮后，由独立进程读取对话，新增、修改或删除事实，不占当前回复的关键路径。Anthropic 的内部商业记忆评估中，这种异步方式让事实召回提高了 13%。

如果让主 Agent 每次调用保存记忆工具，它还得决定要不要记、先查有没有重复、再更新。一串动作插在用户等待回复的时候，既花时间，也可能因为注意力竞争漏记。

提取规则必须清楚。用户表达的尺码、配送偏好，和商品描述、评论里出现的内容，是两种信息。不能因为读过某件商品写着适合运动，就把喜欢运动存成用户的事实。指南建议提取器读取用户与助手的文本，不把工具结果当作用户记忆来源。

读取分三层就比较好理解。默认门店、配送偏好、操作员所属门店和角色，这类几乎每次请求都依赖的少量事实，始终放在上下文里。和本轮任务相关的，利用触发 Skill 加载的同一信号预取：搜鞋子就取尺码和品牌偏好，查活动就取常用指标。剩下的放到查找工具后面，需要时再读，不必让每次请求都背着整份档案。

### 模型提议之后，谁来执行

商业 Agent 一旦涉及订单、支付、退款、改价和活动预算，错误就可能直接变成损失。提示词能约束行为，但真正的执行边界必须在代码里。

指南的核心规则是，模型提出行动，由人或确定的政策机制决定是否执行。工具调用不能绕过框架，直接把钱动了、把业务改了。它可以准备订单、提出退款或价格变更，但最终生效的路径要受控。

这里还有几条很具体的限制。

写入和渲染，只接受服务端签发、在当前流程中可用的 ID。购物车接受本轮服务端返回过的商品 ID，商家工具接受 Agent 真正读过的列表和活动 ID。模型编的、用户粘贴的、评论里藏的编号，在进入后端业务操作前就要拒掉。已有编号也不等于有权限，仍要走相应校验。

限制还要扛得住重复请求。门票配额、优惠额度、预算上限，不能只在单次调用里看起来合规。Agent 可能换一种说法再试，也可能并行发出多个请求。要保证重试不会叠出超额结果。

第三方内容同样不能直接信。商品名、评价、卖家消息和工具结果，都可能夹带伪装成指令的文字，每次后端读取都要按不可信输入处理。清理控制字符和双向字符，移除模仿围栏标记的内容，中和伪装成对话或工具调用的文本，再限制大小。这些处理能减少部分注入风险，但清理过的商品描述依然只是资料，没有资格给系统下指令，权限校验也照常执行。

推荐错一件商品，和错误地执行一笔交易，后果差得很远。我愿意在这里多花些设计时间，“请谨慎操作”几个字承担不了这些责任。

### 评估要能复现那个出错的状态

Agent 是非确定性系统。加一个工具、改一行提示词，都可能影响原来正常的行为，甚至影响到看起来不相关的流程。

快照评估的思路很直接。模型 API 是无状态的，输出取决于这次交给它的系统提示词、工具和消息列表，那就把这些内容连同需要的业务状态构造好，追加一条用户请求，让 Agent 从这里继续跑，再检查最终状态和渲染出的响应。要测长对话里的某个问题，不必每次都从第一句话聊起，盼着它再次走到同一个地方。

对工具调用路径卡得太死，模型稍微换一种合理做法，测试也会失败。更有用的是检查结果是否正确、约束是否遵守，以及用户最终看到了什么。当然，权限和必要的审批步骤本身就是约束，不能因为只看结果而省略。

让模型扮演用户，再请评判者评分，也有价值。但两个非确定性系统聊起来，需要更大的样本量，单次成本更高，评判和故障归因都难。按指南的用法，先让它们帮忙发现案例，再把每个案例写成快照，留作后续回归测试。

测试还要带上失败的前提。某个问题只在长对话里出现，就不能只用干净的第一轮去测。一部分案例应该从混乱、矛盾、有旧约束的历史开始。真实用户不会为了方便测试，每次都把话说得完整清楚。

反向案例是 Anthropic 发现最常见的缺失项。写了“应当拒绝”，也要写什么情况下“应当接受”；写了“必须追问”，就配上信息足够时“应当直接做”的案例。否则测试看着很安全，交给用户的却可能是一个不断打断、什么都不敢继续的助手。

检查用例有没有缺口，可以沿用指南的五类覆盖范围：

- 核心请求。价格、可用性和属性能否追溯到返回数据，缺资料时有没有直说。
- 上下文依赖。能否理解用户指的屏幕内容，以及前几轮留下的条件。
- 安全和品牌。用户消息里的攻击，以及藏在商品名、评论、工具结果中的指令，都要覆盖。
- 界面。组件是否正确，展示数量是否超限，是否把内部标识符暴露给用户。
- 多能力复合。用户问“我降价 15%，库存还够吗”，需要暂存降价方案，同时给出库存预测。只回答定价或只查库存，都只做了一半。

这些案例最好跟一线的人一起写：产品、商家运营、客服、品类、法务，各自知道哪些地方出过错。按指南的建议，每个用户流程先准备五十到一百个案例，再从生产日志里持续补充棘手问题。已经发生过的失败，连同当时的历史和约束一起留下，比只写一个理想化任务更有用。

### 多个团队共同维护，不等于每队配一个 Agent

搜索、结账、定价、营销、客服和目录系统，通常由不同团队负责，各自发布。服务之间可以有清楚的接口，到了 Agent 这里，却可能一起进入同一个上下文。一条定价指令的变化，也可能影响结账行为。

再按部门拆一圈子智能体，并不能消除这些影响。指南把所有权放回已有系统：定价团队负责促销工具和定价 Skill，客服团队负责订单、退货工具，每个 Skill 和工具只有一个明确的 owner。业务知识由熟悉它的人维护，对话仍可以留在同一个 Agent 里。

变更也要带着案例一起交付。新增一个 Skill，除了自己的正向用例，还要提供失败用例，以及与相邻 Skill 交叉时的边界情况。

集成时按影响范围选测试：改 Skill，跑它自己和相邻能力的用例；改工具，跑每个调用它的场景；改共享系统提示词，就跑全套。每次 PR 都跑完整套可能太慢、太贵，只测自己那一小块又会漏掉组合问题，选择性运行需要跟着实际依赖关系走。

提示词和 Skills 也得排进发布日历。先走灰度队列，留一个不下线服务就能关掉单项 Skill 的开关，高峰前冻结变更。一段文字更新，可能同时改变所有用户的体验，发布时就该按这个影响范围来检查，不能因为改的不是代码就省掉流程。

## 回到一次交易怎么完成

读完再回看，里面不少工作其实很熟悉：工具接的是已有系统，Skills 写的是业务流程，评估把产品要求变成测试，运行框架执行本来就该对任何客户端生效的权限和政策。模型参与进来以后，这些工作还在，谁负责也仍得说清楚。

模型当然会继续变好。如果这些边界已经清楚，新模型发布时，团队才有机会主要通过调整配置、重跑评估来完成升级，而不必重新梳理整套业务。

比起一开始选多少个 Agent，我更愿意先把一次交易写清楚：从用户提出需求到订单生效，哪里要确认，谁有权执行，失败了从哪一步继续。模型能承担哪些部分、需要多快、一次完成花多少钱，都放回这条流程里讨论。
