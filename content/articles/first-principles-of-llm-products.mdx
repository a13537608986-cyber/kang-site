演示视频里的 LLM 产品总是流畅、聪明、不出错。但放进生产环境，支配它的只有三个变量：概率、成本、延迟。它们不是工程细节，而是产品决策的边界条件。本文以 GPT-4 一代模型为参照，谈谈我对这三个变量的理解。

## 概率：输出是分布，不是返回值

传统软件的函数给定输入就给定输出，测试通过即可上线。LLM 不是这样：同一个 prompt，今天和明天的回答可能不同；temperature 设为 0 也只能降低方差，不能消除。这意味着"它有时会错"不是 bug，而是产品的物理属性。

由此推出的判断是：不要试图让模型不犯错，而要设计犯错时的承接路径。示例场景：一个客服摘要工具，与其追求摘要绝对准确，不如在界面上保留原文对照入口，把人工校验的成本压到足够低。准确率从九成提到九成五可能要十倍努力，一个好的兜底交互只要一周。

看一个团队是否真懂概率属性，看验收标准怎么写：写"输出必须正确"的还没入门；写"错误可被发现、可被纠正、不造成不可逆损失"的，才是在做 LLM 产品。

## 成本：token 是真金白银

API 按 token 计费，改变了软件的成本结构。传统 SaaS 的边际成本趋近于零，LLM 产品的边际成本随用量线性增长，而 GPT-4 级别的调用并不便宜。"用户用得越多越好"这条增长教条要打折扣——重度用户可能是亏损来源。

几个 2023 年就能落地的成本动作：

- 分层调用：简单任务走小模型或规则引擎，复杂任务才上 GPT-4
- 控制上下文长度：把整篇文档塞进 prompt 是最常见的浪费
- 缓存高频问题的结果，相同输入不重复计费
- 定价里预留用量分层，不轻易承诺无限量

成本不是上线后再优化的事。如果单次调用成本乘以预期调用量，得出的数字撑不起定价，这个产品形态本身就不成立。

## 延迟：决定交互形态

GPT-4 生成几百字往往要十几秒，这个速度直接决定产品长什么样。流式输出成为标配不是炫技，而是把"等待十秒"变成"等一秒后开始阅读"。延迟无法消除，只能被交互设计吸收。

判断标准很简单：这个场景能容忍几秒？搜索框背后的意图理解要求百毫秒级响应，把 LLM 直接放进去就是不及格；写作助手可以容忍十秒，因为用户本来就要花几分钟构思。反例：把 LLM 嵌进表单自动填充，每个字段等三秒，用户手动填反而更快——延迟就是这样杀死一个看似合理的形态。

## 所有决策都是三者的交换

概率、成本、延迟互相牵制：要更准，就用更大的模型、更长的推理链，于是更贵、更慢；要更快更便宜，就要接受更高的错误率。不存在三者皆优的方案，只存在适合特定场景的取舍。

所以评审一个 LLM 产品方案，我只问三个问题：错了怎么办，贵了怎么办，慢了怎么办。三个问题都有具体回答的方案，才值得往下推。演示效果回答不了其中任何一个。
